# CLAUDE.md

Stubbase: multi-tenant, scale-to-zero JSON-to-CRUD hosting for a 1GB VPS. See README.md for architecture and API details. Canonical domain is **stubbase.dev** (we do not own stubbase.com).

## Hard constraints

- **Bun only** on the backend — no Node.js, Express, PM2, or ts-node. Use `Bun.serve`, `Bun.file()`, `Bun.write()`, `bun:sqlite`, `Bun.password`. The two backend apps must stay at **zero npm dependencies**.
- **Caddy only** for proxying/static files (no Nginx). Static zones (`stubbase.dev`, `app.stubbase.dev`) are served by Caddy alone — the frontends must always build to static `dist/`; never add a backend process (SSR, API routes) for them. The single exception is `stubbase.dev/auth/google/one-tap`, which Caddy proxies to the Dashboard API: the One Tap `g_csrf_token` is a **host-only** cookie, so the form POST carrying the credential has to land on the host that rendered the prompt or the cookie never arrives. That adds no process and the site still builds to static `dist/` — but it is the only non-static path on the apex, and a second one needs the same justification.
- Production runs under **systemd** (no Docker); Docker Compose is for local dev only. Deployment is **Ansible** (`deploy/deploy.yml`).
- Everything is sized for 1GB RAM: keep per-request allocations small, preserve the memory caps, keep argon2 params modest.
- **`ADMIN_SECRET` never reaches a browser.** The SPA must not call the core `_admin` plane; all file writes go through the Dashboard API's authenticated files proxy (`PUT/DELETE /projects/<id>/files/<res>`).
- **The landing site and the SPA are different origins, and only two cookies cross that line.** `stubbase.dev` is static and `app.stubbase.dev` is the SPA, so localStorage cannot carry state between them; `stubbase_theme` (the chosen theme) and `stubbase_session` (a *hint* that a session exists) are scoped to the registrable domain instead. The hint carries **no token and authorises nothing** — it only decides which nav links a static page renders. The session token stays in the SPA origin's localStorage: a domain-wide cookie would hand every subdomain a bearer credential. `sites/dashboard/src/lib/cross-site.ts` is the writer; the two inline pre-paint scripts that also read them (`sites/dashboard/index.html`, `sites/landing/src/layouts/BaseLayout.astro`) cannot import it — they run before any bundle exists — so keep the cookie names and the domain rule in step across all three.

## Commands

```bash
# whole dev stack in one process: both backends (--watch) + both dev servers,
# prefixed output, one Ctrl-C. Owns the dev ports; seeds the `public` demo
# tenant on first run. Dev-only supervisor — nothing in prod depends on it.
bun run scripts/dev.ts        # dashboard :5173, landing :4321, core :3000, app :3001

# backends individually (no Docker)
ADMIN_SECRET=dev PORT=3000 bun run apps/core/server-core.ts
ADMIN_SECRET=dev PORT=3001 CORE_API_URL=http://127.0.0.1:3000 bun run apps/dashboard-api/server-app.ts

# frontends — three environments: dev (vite/astro dev servers + proxy,
# .env.development → localhost cross-links), docker (`build:docker`,
# .env.docker → *.localhost), prod (`build`, *.stubbase.dev)
cd sites/landing   && bun run build     # Astro SSG → dist/ (build:docker for the local stack)
cd sites/dashboard && bun run build     # Vite SPA → dist/ (build:docker for the local stack)
cd sites/dashboard && bunx vite         # dev server; proxies /api/app → :3001, /api/core → :3000

# full local stack (Caddy on :80, *.localhost hosts)
docker compose up --build

# regenerate the guides' AI Summary panels (never part of the build — see below)
bun run scripts/ai-summary.ts            # guides whose summary is missing or stale
bun run scripts/ai-summary.ts --check    # CI: fail if a guide drifted from its summary

# top-level build: verify + test the backends, then build both sites.
# Maven-style reactor log; fail-fast, so a red module skips everything after it.
bun run scripts/build.ts               # prod URLs → sites/*/dist/
bun run scripts/build.ts --docker      # build:docker mode for the local stack
bun run scripts/build.ts -pl core      # one module: core|dashboard-api|landing|dashboard
bun run scripts/build.ts --skip-tests  # escape hatch; test goals report SKIPPED

# deploy / syntax-check  (run the top-level build first — dist/ is gitignored)
cd deploy && ansible-playbook --syntax-check -i inventory.ini.example deploy.yml
STUBBASE_ADMIN_SECRET=... ansible-playbook -i inventory.ini deploy.yml
```

`scripts/build.ts` is the gate; Ansible only ships whatever `dist/` it finds, and **not deploying after a failed build is the operator's call** — the script deliberately leaves a previous `dist/` in place. The backends have no build step, so their reactor modules exist purely to run the zero-dependency check and the regression suite: that makes this script the only thing between a broken `server-core.ts` and production.

Tests live in top-level `tests/`, run by `bun test` (built into Bun — no npm dependency). `tests/core.test.ts`, `tests/dashboard-api.test.ts`, `tests/starters.test.ts`, `tests/playground.test.ts` and `tests/log-storage.test.ts` are wired into the matching reactor modules (the last three into `dashboard`); a suite that doesn't exist reports SKIPPED rather than failing the build. Those three are the suites that import frontend code, and only React-free modules: the starter-example *data* in `sites/dashboard/src/lib/starters.ts`, seeded into a real core so each card's advertised `?_expand=…` query is verified rather than duplicated; the playground's request model in `sites/dashboard/src/lib/playground.ts`, whose URLs and headers are checked against a real core's router and CORS preflight; and the Logs pane's storage rules in `sites/dashboard/src/lib/log-storage.ts`, held against real log entries from a real core's auth routes. `tests/helpers.ts` (outside bun test's glob) spawns each backend as a real process on an OS-assigned port against a scratch `TENANTS_DIR`/`DB_PATH` — the dashboard-api suite runs a real core alongside it, since the files proxy and draft model only mean anything end-to-end.

**Keep them black-box.** Nothing imports server internals, so refactoring the pipeline, dispatcher or storage layer doesn't touch the tests — they fail only when observable behaviour changes. The invariant lists below are the spec; when you add an invariant, add the test. Verify a new test actually bites by breaking the invariant on purpose and watching it go red. Verify frontend changes with a production build plus a real-browser pass (dev server + headless Chrome), not just `tsc`.

## Core Engine invariants (apps/core/server-core.ts)

Breaking any of these is a correctness bug:

- **Write-through**: every mutation updates the in-RAM array *and* immediately persists via the per-tenant `writeChain` promise chain (serializes `Bun.write` so concurrent mutations can't interleave a file). Never mutate RAM without persisting.
- **Admin invalidation**: any `_admin` route that touches a file must call `evict(tenantId)` afterward so the next request lazy-loads fresh disk state.
- **Name validation**: tenant ids and resource names must pass `NAME_RE` *before* any filesystem path is built — this is the only path-traversal defense.
- **Eviction is safe** only because of write-through: eviction just drops the Map entry, it does not flush anything.
- Admin auth uses hashed `timingSafeEqual` — keep it constant-time.
- **CORS split**: public CRUD routes (and their error responses) send `Access-Control-Allow-Origin: *`, and the public preflight allows `authorization` (tenant JWTs ride that header); the `_admin` plane sends no CORS headers and *its* preflight must not allow the `authorization` header. Keep it that way.
- **Tenant layout: `data/` and `system/`.** `data/` holds the resources and their `draft_*`; `system/` holds `config.json` and `rbac.json` (with their drafts), `status.json`, and the files a feature owns. Only `data/` is loaded into `state.db`, so nothing in `system/` can ever be served, expanded, described in `openapi.json` or mounted for SQL — that is the whole defence, so keep feature files out of `state.db` rather than filtering them out downstream. `_admin/files/<name>` resolves by name (`adminFile`): the settings files `config` and `rbac` and their drafts → `system/`, everything else → `data/`, so a feature file is unreachable from it. Feature files are read only through `GET _admin/system[/<file>]` (read-only, credentials stripped by `viewSystemFile`) and written only by their feature through its host (`persistSystem`, on the same `writeChain` as the resources). Deploy promotes each draft within its own folder, and in `system/` promotes config and rbac alone. Files in the tenant root are not read, and there is no migration from the old flat layout — nothing was ever deployed on it.
- **Tenant auth** (`AUTH_ENABLED`, in `apps/core/features/auth/`): per-tenant JWT signing keys are *derived* from `ADMIN_SECRET` (HMAC over the tenant id) — never stored on disk. The identity table is **`system/users.json`, never a CRUD resource**; it leaves the server only through `safeUser` (auth responses) and `viewSystemFile`. A `data/users.json` is an ordinary resource with no special handling — do not reintroduce any. `auth` and `config` are reserved names, never CRUD resources. **Every JWT consumer calls `auth.authenticate`, never `verify` alone** (authGuard, `_notify`, change-password): it also requires the token's user to still exist and its `pwdAt` claim to equal the user's `passwordChangedAt`, which is how changing or resetting a password signs that user out everywhere — and it reads the role from the user record, not the token, which is why a role change applies from the next request with no new token. A new account gets `rbac.json`'s `defaultRole` (or `user` without rules), and a role is changed only by `setRole` in `features/auth/users.ts`: from the dashboard through `_admin/users/<id>/role`, or by a role holding `_users: update` through `PUT /auth/users/<id>/role`. Either way the role must exist in the rules in force.
- **Password reset is a 6-digit code, and the limits around it are the security** (`password-reset.ts`): 15-minute TTL, spent by its first correct use, five wrong guesses spend it, a new request replaces the previous code, and at most five codes per user per hour counted from the row's persisted `issuedAt` — so a row outlives its code, because deleting it would reset the throttle. Codes are stored as an HMAC under a key derived from `ADMIN_SECRET`, never a bare hash: a million candidates is nothing to brute-force, and the dashboard shows the file. `forgot-password` answers the same `202` for every address and throttles silently; `reset-password` gives one error for every way a code can be wrong; and a correct code is spent *before* the password hash awaits, so two racing requests cannot both use it. Mail goes through the tenant's own Resend key (`sendEmail`, shared with `_notify/email`); `AUTH_RESET_LOG_CODES=true` prints codes to the log for local dev and tests only — never in production. `tests/core.test.ts` breaks each limit.
- **A feature never imports `server-core.ts`.** That module starts the server as it loads, so a feature is built once by the core from a host object (`createAuth(host)`) carrying what only the core can do — load a tenant, persist its files, refuse a stopped or over-quota project, send email. New per-feature behaviour goes behind that host, and anything that builds a public-plane body uses `lib/http.ts`'s `json()`, or metering and logging silently lose it.
- CRUD requests flow through the middleware `PIPELINE` (`statusGuard → quotaGuard → authGuard → rbacGuard → chaosGuard → validationGuard → beforeWebhookGuard → coreOperation → afterWebhookGuard`); new per-request behavior belongs in a pipeline stage, not in the dispatcher. A stage returns a `Response` to abort, or `SKIP_REST` when it has already set `ctx.response`.
- **Protected names**: `isPrivateFile` (config/stubbase/env/`draft_*`) never mounts as a servable resource, and `isProtectedResource` (those plus `_`/`.` prefixes) answers **403** on the public plane. Internal planes (`_admin`, `_notify`, `auth`, `openapi.json`) are dispatched *before* that check — keep them there or the blacklist will swallow them.
- **QA chaos headers** (`x-stubbase-delay|status|error-rate|empty`) only act when the tenant sets `QA_MODE=true`, and `chaosGuard` runs *after* `authGuard` so simulation can never bypass auth. Delay is capped by `MAX_CHAOS_DELAY_MS`.
- Schema validation is a **built-in** subset validator (`validateSchema`) — do not add ajv/zod; the backends stay dependency-free.
- **Usage metering**: public-plane responses are counted in the `usage` Map (the `_admin` plane is not). Two exceptions, both deliberate. **Refusals are logged but not metered**: the 503 `statusBlocked` returns and the 429 `quotaBlocked` returns are marked in the `refusals` WeakSet where they are built, because the project served nothing and counting them would push `used` past the limit it is being held to — marked at the source, never recognised by status, since a QA project's `x-stubbase-status` 503/429 is real traffic and is counted. **A tenant with no directory is answered 404 before metering and logging** (`tenantExists`, placed after the `_admin` dispatch because an admin write is how a tenant is born): both key on the URL's id, so counting a made-up id mints a usage row, a quota entry and a log ring for nobody, and the in-RAM two are never freed — only a tenant that loaded is ever evicted. Responses are otherwise counted whatever their status and flushed to the Dashboard API's `/_internal/usage` every `USAGE_FLUSH_MS`, on eviction, and on shutdown. Counters deliberately live *outside* `activeTenants` so eviction can't drop them, and a failed flush folds its counts back in rather than losing them. `json()` sets `content-length` so metering never has to clone a body — keep it that way.
- **Request quota**: the core is **plan-blind** — it never learns what a plan is. The Dashboard API answers each usage flush with one number per tenant (`quotas: [{ tenantId, limit, used }]`) — and `used` is the owning **account's** month-to-date total across all its projects, since the allowance is one pool per account (see the Dashboard API's plans invariant); the reply quotes every project of an account that reported, so its idle projects stop together. The core serves until `used >= limit`, then `429`s the whole public plane (`quotaGuard` for CRUD, `quotaBlocked()` in the auth/notify/openapi handlers — add the call to any new public route), with `_admin` still reachable so the owner can see why their API stopped. `quotaGuard` sits *before* `authGuard`: an exhausted project should stop costing the box work, and a 429 that demanded a token would be unreadable to the client being throttled. Between flushes the count advances locally, so overshoot is bounded by `USAGE_FLUSH_MS`. **Deliberately fail-open**: a tenant that has never been quoted a limit is served — breaking a customer's CI because metering hiccupped is worse than over-serving for a minute. Like the usage counters, `quotas` lives outside `activeTenants` so eviction can't hand out a fresh allowance.
- **Live request log**: every public-plane response gets an `x-correlation-id` and one entry in the tenant's capped in-RAM ring (`LOG_CAP`, oldest dropped first); bodies are truncated to `LOG_BODY_CHARS`. Nothing is written to disk. Like the usage counters, the ring and its SSE subscribers live **outside `activeTenants`** so an idle eviction can't blank a log someone is watching — eviction drops the ring only when nobody is subscribed. The `_admin` plane is never logged. `GET /<tenant>/_admin/sse-logs` replays the ring then streams; `GET /<tenant>/_admin/logs` returns the same ring as a one-shot snapshot (`_limit` takes the newest N) for callers that need the log as data inside one request — the AI Co-Pilot's diagnostics tool, which must not leave a subscriber behind on every call. Both are admin-authenticated and CORS-free like the rest of that plane, so browsers reach them only via the Dashboard API proxy. `json()` stashes its serialized body in a WeakMap so logging never clones a response body — keep that, for the same reason `content-length` exists.
- **Virtual start/stop**: `system/status.json` (`{ "status": "active" | "stopped" | "maintenance" }`) — `stopped`/`maintenance` makes every public surface 503 (`statusGuard` for CRUD, `statusBlocked()` in the auth/notify/openapi handlers — add the call to any new public route). `_admin` must stay reachable when stopped, or a stopped project could never be restarted. **Status is not config, and must never become a config key again.** Its one writer is `POST _admin/status` (the dashboard's Start/Stop and the Co-Pilot's `set_server_status`, both through `applyProjectStatus`); it is never staged, never promoted by deploy and has no `.env` line. As a config key it had two writers with different rules, and an editor opened while running, saved after Stop and then deployed, started the API again — `tests/dashboard-api.test.ts` holds that case. An absent or unreadable file reads as active, in the core and in the Dashboard API's delete guard alike.
- **Draft model**: dashboard writes go to `draft_<name>.json` beside the file they stage (`data/`, or `system/` for config); `loadTenant` skips `draft_*` so staged files are never served, and `_admin/deploy` copies each draft over its live file, **deletes the draft**, then evicts. Consuming the draft is load-bearing, not tidiness: drafts are read in preference to live files, so a leftover one is a frozen second copy of the resource that nothing updates again — it hid every record the public API created from the dashboard editor, and the next deploy re-promoted it over the live file and destroyed those records even for a resource nobody had edited. The delete happens only after the copy lands, so a failed write leaves the staged edit intact. Only the core may write `TENANTS_DIR` (the dashboard's systemd unit can't), so deploy/flush live on the core admin plane and the dashboard calls them over HTTP.
- **The SQLite projection is a projection, never the store.** The JSON arrays stay authoritative; `buildSqlMount` derives a read-only `:memory:` database from them on first SQL use, and `persist()` and `evict()` drop it so the next query rebuilds (~1ms). Never route CRUD through SQL: records are heterogeneous, so a schema taken from one row silently loses every key the other rows carry the moment a table is dumped back to disk — the mount unions keys across **all** rows for exactly that reason. It lives outside `activeTenants` with its own `SQL_IDLE_MS` timer, like the log ring, because an MCP session outlives tenant eviction.
- **The SQL surface is read-only, and it takes two layers** — both load-bearing, neither decorative. `PRAGMA query_only = ON` is what stops writes, including ones the text check can't see (`WITH x AS (…) DELETE FROM …` starts with `WITH`). The "must start with SELECT or WITH" check is what stops `ATTACH`, which `query_only` does **not** block — without it an agent could attach the Dashboard API's `app.sqlite` on the same box and read its `users` and `sessions` tables. Removing either one is a security regression; `tests/core.test.ts` has a case for each.
- **Only `data/` is ever mounted.** The projection reads `state.db`, which never holds `system/`, so the identity table, reset codes, `config` and `draft_*` cannot be queried: a table that was never created cannot leak through `SELECT *`. Keep it structural — never mount a feature file and filter its columns instead.
- **MCP tenancy is pinned at connect time.** The tenant comes from the URL path when the SSE stream opens and is stored on the session; `POST …/mcp/message` refuses a session whose tenant doesn't match its path, and the JSON-RPC dispatch reads `session.tenantId`. Nothing inside a message may select a tenant — that is what keeps multiplexed sessions from cross-contaminating. MCP sits on the `_admin` plane so `ADMIN_SECRET` authorizes it and it stays CORS-free, unmetered, and unable to collide with a resource named `mcp`.
- **Webhook SSRF guard**: tenant-supplied `HOOK_*` URLs are DNS-resolved and refused if they hit private/reserved addresses (`hookUrlBlocked`), with `redirect: "manual"` on the fetch. `HOOK_ALLOW_PRIVATE=true` bypasses this for the local stack only — never set it in production.
- **Ownership without rules**: authenticated POSTs stamp `userId`; non-admins may mutate only records they own (`userId === sub`, or records with no owner) and cannot reassign `userId` — role `admin` bypasses. Every resource is treated alike, `users` included, since accounts are not a resource. This is what a project with `AUTH_ENABLED` and no `rbac.json` gets, and it must keep behaving exactly so.
- **Roles and permissions (`system/rbac.json`, `features/rbac/`)** replace those ownership rules once `AUTH_ENABLED` and `RBAC_ENABLED` are both on *and* the file exists (`rulesOf`); with either switch off, a file on disk is inert. The file can only be written while both switches are on in the settings being edited — the Dashboard API's `rbacSwitchedOn` reads `draft_config`, else `config`, and answers 409 — because it is saved and deployed alongside those settings. A permission is resource + action (`read`/`create`/`update`/`delete`, from the method) + scope (`own`/`all`); a role is a bundle of them; `rbacGuard` runs `decide` and hands `coreOperation` the scope. Rules that must hold:
  - **Deny by default.** A resource or action a role doesn't list is refused; a role missing from the rules has no permissions. A refused visitor gets 401 (signing in might help), a refused account 403 naming its role.
  - **`own` is enforced on the server, in every path**: lists are filtered *before* filters, paging and `X-Total-Count`; a single record outside scope reads as 404; update/delete outside scope answer 403 when the role can `read` all (the record is visible) and 404 otherwise; `create` with `own` stamps the caller's id whatever the body says; `update` with `own` can never move `userId`. `admin` gets no bypass under rules — `"*"` is how a role gets everything.
  - **`guest` is the role for requests without a token**, may hold only `all` scopes and no `_users`, and while rules exist `AUTH_PUBLIC_ROUTES` is ignored. A token that fails verification is 401, never downgraded to guest.
  - **Rules are validated where they are written** (`_admin/files/{draft_,}rbac` → 400 with `problems`, which the Dashboard API passes through), and a file broken on disk **fails closed**: it loads as no roles, so everything is refused rather than open. Every mistake is reported, never skipped — a silently dropped permission reads as a working file.
  - `rbacGuard` sits after `authGuard` (the role comes from a verified token) and before `chaosGuard` (a simulated response must never stand in for a refusal). `rbac` is a reserved name everywhere a resource name is checked. `tests/core.test.ts` breaks each rule.
- **Timestamps are server-owned.** Every public-plane write stamps them through `newTimestamps()`: a POST, a signup and an OAuth first login set `createdAt` and `updatedAt`; a PUT keeps the stored `createdAt` — and never invents one for a record that had none — and sets `updatedAt`. Whatever a client sends for either field is overwritten, because a PUT that echoes a fetched record would otherwise send its old `updatedAt` straight back and freeze it. The `_admin` plane never stamps: a file written from the dashboard keeps exactly what it contains. `_sort=created|updated` sorts by them and defaults to newest first, every other key to ascending; `_direction` replaced `_order`, which is no longer read; and a record missing a sort field goes last in either direction.
- **Filters: plain is exact, brackets are operators, typos are errors.** `field=value` stays an exact, case-sensitive match — ids, enums and ownership lookups depend on it, so it must never turn fuzzy. `field[contains|gt|gte|lt|lte]=value` (`parseFilters` / `matchesFilter`) adds the rest: `contains` folds case and accents over text and arrays of text; the comparisons order numbers numerically and text naturally, which is what makes ISO timestamps range-filterable. An unknown or empty operator is a 400, never ignored — silently dropping a misspelt condition returns everything and looks like success. (No field needs a filter ban any more: the password hashes that once did live in `system/`, which no filter can reach.)
- OAuth (`AUTH_GOOGLE_*`/`AUTH_GITHUB_*`), reset emails and the `_notify` proxy (`RESEND_*`/`TWILIO_*`) read tenant-owned credentials from `system/config.json`; upstream endpoint URLs are env-overridable strictly for mocking in dev/tests.

## Dashboard API invariants (apps/dashboard-api/server-app.ts)

- Auth is real: argon2id via `Bun.password` (OWASP params), opaque bearer session tokens stored **sha256-hashed** with TTL. Login must verify against a dummy hash when the email is unknown (no timing-based user enumeration).
- **Dashboard OAuth is a different thing from tenant OAuth, and the seam matters.** `DASHBOARD_GOOGLE_*`/`DASHBOARD_GITHUB_*` are *Stubbase's* OAuth apps, read from process env, signing people into the dashboard; a tenant's `AUTH_GOOGLE_*` lives in that project's `config.json` and signs in that project's end users. Three rules hold the sign-in together: the callback only proceeds on a **state** it minted itself (HMAC over provider+timestamp+nonce, keyed by a hash of `ADMIN_SECRET`, 10-minute TTL, `timingSafeEqual`, provider bound in so a Google state can't be replayed at GitHub); an **unverified email is refused** (`email_verified` for Google, the `/user/emails` entry for GitHub — never the GitHub profile's own `email`, which nobody verified), because an OAuth identity is linked to an existing account *by email* and an unverified one is an account-takeover primitive; and the session rides back to the SPA in a **URL fragment**, to a `DASHBOARD_URL` that is a constant — a `return_to` parameter here would be an open redirect handing out session tokens. An OAuth-created row has a NULL `password_hash`, and `login()` must keep refusing those rather than verifying against nothing.
- **Google One Tap is the same sign-in with a different first leg, and it is the one route that lives on the landing origin.** A signed Google ID token is POSTed to `POST /auth/google/one-tap` instead of us exchanging a code, so there is no `state` and no client secret — the token's own claims are the entire proof, and all of them are checked: RS256 pinned by name (never trust the header's `alg`), the signature against Google's JWKS, `iss`, `exp`, and `aud` against **our** client id, since a token minted for any other site is a perfectly valid Google token. `email_verified` is refused exactly as in the redirect flow, because both paths end in `signInWithIdentity`, which links by verified email — keep that helper shared so the two can never drift. The endpoint is served from `https://stubbase.dev/auth/google/one-tap` via a Caddy path proxy and **cannot move to the API subdomain**: `g_csrf_token` is host-only, so the double-submit check would never see the cookie. **One Tap ignores `ux_mode`/`login_uri`** — Google's reference is explicit that ux_mode has no impact on the One Tap UX, and under FedCM the browser hands the credential to the page's `callback`. Configured for redirect the prompt renders and the tap silently does nothing, which is exactly how this shipped once. So Home's callback form-POSTs the token to this same path itself, and `g_csrf_token` is a double-submit pair the *page* mints (Google only sets that cookie when Google is the one posting). The landing page therefore does hold Google's ID token for an instant — short-lived and `aud`-pinned, and re-checked here — but never a Stubbase session token: the 302 carries that to the SPA in a fragment, which is what keeps the cross-origin cookie rule intact. It must stay a form submission; `fetch` would follow the 302 and swallow the fragment.
- Every `/projects*` route is scoped to the authenticated user — ownership-check before any core admin call.
- The files proxy must keep the project's `resources` column in sync with what it creates/deletes on the core, and **the whole read-modify-write of that column must sit in one synchronous turn** — `addResources`/`removeResource` re-read it themselves for exactly that reason. `putFile` and `deleteFile` hold a project row from *before* their call out to the core, and Bun.serve interleaves other requests during that await, so rebuilding the list from that snapshot silently drops whatever landed in the meantime: two concurrent creates each write back a list that never saw the other, and a delete erases a resource created alongside it. The files reach disk either way and every call returns 200, so the only symptom is a resource missing from the sidebar with no error anywhere. Never rebuild this column from a row read before an await.
- **`dirty` records the edit, not the draft file.** It is what tells a *running* project's dashboard that its live API is behind. Deploy now consumes the draft it promotes, so draft-existence and `dirty` agree in the ordinary case — but the flag stays the authority, because it records the *edit* while the file records only what is currently staged, and the two come apart whenever a write lands without one: a delete stages nothing, and a refused deploy leaves the draft in place. Do not switch the dashboard back to reading disk for this. It is also what orders the editor's reads (`getFile`): the draft wins while an edit is staged, the live file wins otherwise, and **both are always tried** — preferring the draft unconditionally is what hid a project's own API writes behind a snapshot stranded by a pre-fix deploy, while trusting the flag alone would 404 a resource that exists only as a draft. The flag was added by `ALTER TABLE` defaulting to 0 and deliberately never back-filled, so on any project older than the column it is a hint, not proof — never let it be the only thing deciding whether a file gets read. `?source=live` on that same route is the **other** question: not what is being edited but what the public plane is serving, so it reads the production file alone, with no draft and no fallback. The SPA's APIs rail is its caller — the routes a project exposes follow its *deployed* config, so staging `AUTH_ENABLED` must neither add the auth routes nor, cleared, retire them until the deploy that actually moves them. Anything describing the running API reads live; anything describing the edit reads the default. Every writer of a draft therefore calls `markDirty` — `putFile` and the Co-Pilot's `stage_schema_drafts`, which writes through `coreAdmin` directly — and `promoteDrafts` calls `clearDirty` **on success only**, so a refused deploy leaves the changes flagged. Every ambiguity resolves toward over-reporting, including a delete, which stages nothing but leaves the flag alone because one boolean cannot say whether *other* resources are still staged: a redundant redeploy is cheap, and a clean-looking dashboard over stale data is not. Add a draft writer, add the `markDirty` call — nothing on disk can correct a miss.
- Browser CORS is allow-listed via `ALLOWED_ORIGINS` (default `https://app.stubbase.dev`) — never `*` on this service.
- `GET /projects/<id>/live-logs` proxies the core's admin SSE stream after an ownership check, passing the upstream body through unbuffered and forwarding the client's abort signal (so a closed tab tears down the core-side subscriber). The SPA consumes it with `fetch` + `ReadableStream`, **not `EventSource`** — EventSource can't set an Authorization header, and moving the session token into the query string would leak it into proxy logs.
- **Developer API keys are sha256-hashed, not argon2id — on purpose.** They are 256-bit CSPRNG secrets this service mints itself, so there is no dictionary for slow hashing to defend against, and salting would forbid the indexed lookup-by-hash that `developerKeyAuthorizes` depends on. Argon2 would instead force a scan-and-verify over the project's keys at ~19 MiB each, on every MCP message POST — a denial of service on the 1GB box. Same treatment as session tokens, for the same reason. User passwords keep argon2id.
- **`GET|POST /projects/<id>/mcp/*` authenticates with a developer key, never a session token**, so it is dispatched *before* the session check in `route()`. The key lookup is scoped by `tenant_id`, so a valid key can only ever open its own project; the tenant always comes from the path. Revoking a key, or deleting the project, must invalidate it — `deleteProject` clears `developer_api_keys` so credentials never outlive the tenant id they name.
- **Key ids are revoked with `WHERE id = ? AND tenant_id = ?`.** The ownership check alone is not enough: an attacker owns the project named in the URL, so `ownedProject()` passes, and only the tenant clause stops the id reaching another project's key.
- **The MCP SSE proxy rewrites the first `endpoint` frame and nothing else.** The core names its own `_admin` path there, which no external client can reach; the proxy rebases it onto `/projects/<id>/mcp/message`, keeping it *relative* so it resolves against whatever origin the client used. Everything after that frame is forwarded byte-for-byte — buffering the stream would defeat the point of SSE.
- `GET /projects/<id>/diagnostics` reports JSON files that fail to parse (live resources, their drafts, and `config`), read over the core's admin files plane — this service can't read `TENANTS_DIR` itself.
- **A new project's `.env` is a template, all of it commented out.** `createProject` writes `envTemplate(tenantId)` into `__raw`: every setting the core reads, grouped by feature with a comment each (plan names from `PLANS`, OAuth callbacks the project's own), all commented out — so a new project compiles to an empty config and the template switches nothing on. Status is deliberately not in it (see the core's Virtual start/stop invariant); `createProject` writes `status.json` first, before any resource, so seeded records are never served. **Anything that sets a key from code writes it into `__raw` too, uncommenting the template's line in place** — `mergeEnv`/`setEnvLine` in the SPA (both starter paths). A key set only in the object is live but still commented out in the editor, and the next Save silently switches it back off. `tests/dashboard-api.test.ts` holds the template to the keys the core reads: a new tenant config key goes into `envTemplate`, that test's list, the SPA's `KNOWN_KEYS` and ENVIRONMENT.md together.
- **`GET /projects/<id>/system[/<file>]` is read-only, and has no write twin on purpose.** It proxies the core's `_admin/system` plane after the ownership check, so an owner can see who has signed up. Feature files change only through the feature's own public routes (signup, reset-password, …): a dashboard edit to `users.json` would bypass hashing, revocation and the reset limits all at once. The one exception is an account's role (`PUT /projects/<id>/system/users/<userId>/role`), which goes through the core's `setRole` exactly like the public route, so the role must exist in the rules.
- **Plans differ by request allowance alone.** `PLANS` (free / pro / pro_ai) is the single source of truth; an unknown plan string reads as Free, **never** as unlimited. Every project feature — auth and roles, webhooks, QA mode — is on every plan, so nothing a project's `.env` or `rbac.json` switches on is refused and deploy re-checks nothing. The one gated feature is the AI Co-Pilot (`features: ["ai"]`, Pro + AI), refused by its own route because every turn is a paid provider call; don't gate a project feature again without a reason of that kind. The *request allowance* is gated at **request time** in the core, the only thing in the traffic path. It is **one pool per account, never per project**: `quotaFor` sums everything the account was charged this month, so another project never buys another allowance. Each `api_usage` row records the account it was charged to (`user_id`, set at ingest) rather than being joined through `projects`, because that join would forget every deleted project and make delete-and-recreate a reset; platform tenants are charged to nobody, even if a project row names an owner. There is no payment gateway: a plan is set with `UPDATE users SET plan = …`, and `scripts/seed-dev-users.ts` makes one account per plan locally.
- **Platform tenants are metered but never limited.** Tenants in `PLATFORM_TENANTS` (default `public`, the landing site's demo) are counted but never quoted an allowance; they are omitted from the flush reply so the core's fail-open path covers them with no special case.
- **The Co-Pilot's plan check runs before the provider check**, so a Free account gets the same 402 whether or not this deployment holds an API key — the refusal must not double as a probe of the server's configuration. Ownership still comes first: a stranger gets 404, not a plan lecture.
- **The AI Co-Pilot is an agent loop, and this service owns it** (`POST /projects/<id>/ai/chat`). The provider returns either prose or a tool request; this service executes the tool, feeds the result back, and re-asks, bounded by `AI_MAX_TOOL_ROUNDS` with a final tool-less round so a turn always ends in a sentence. Four things are invariant: the **tenant comes from the authenticated path, never from a tool argument**; tool calls are executed only from a *live model reply*, never from the history the browser sent; every argument is validated like a request body (`stage_schema_drafts` writes `draft_*` only, `set_server_status` accepts only the two states its declaration advertises); and **the agent may not destroy data** — `delete_resources` only returns a `pendingConfirmation` naming resources that actually exist, and the deletion is carried out by the user's click against the ordinary files routes. Keep it that way: a tool that both decides *and* deletes turns a fuzzy "clear all data" into an irreversible one.
- **A tool that cannot do what was asked must say so as a capability limit, not a schema error.** Told its arguments were malformed, a model retries with something structurally valid: refusing an empty `stage_schema_drafts` with "'tables' must be a non-empty array" is what once produced a fabricated `placeholders` table, a deploy, and a false "all data has been cleared". The refusal text names the right tool and forbids filler tables, and the persona's HONESTY rule forbids reporting work no tool performed. The conversation is stateless server-side — the SPA round-trips it — so `messages` is untrusted input with size and shape caps.

## Layout / conventions

- `apps/core/` and `apps/dashboard-api/`: one main `.ts` file each plus `package.json` and `Dockerfile`. The core's exceptions are `lib/` (helpers the core and its features share — `http.ts`, `names.ts`, `timestamps.ts`) and `features/<name>/`, one folder per feature offered to projects: `auth` and `rbac`. The Dockerfile and the Ansible task copy those two directories whole, so a file added inside them ships on its own; a new top-level directory needs both updated. Config comes from env vars only (same knobs in docker-compose, systemd units, and dev). **ENVIRONMENT.md is the canonical env-var/tenant-config reference — update it when adding or changing any knob.**
  - The one exception is `apps/dashboard-api/ai/` (provider-agnostic AI module: `ai.interface.ts`, `google-ai.service.ts`, `prompts.ts`, `index.ts`) — swapping AI providers must not touch routes. `IAIService.chat()` is deliberately one round-trip: the provider file is pure transport, and the agent loop stays in `server-app.ts`, which is the only side that knows about tenants. `prompts.ts` owns the persona *and* the tool catalogue (`CO_PILOT_TOOLS`) because both are the agent's capability surface, not a Google detail; the provider file translates them to the wire. Still zero npm dependencies. **Adding files here means updating both the Dockerfile `COPY` and the Ansible copy task**, or production ships a broken import.
- **AI output is untrusted input**: generated table names are validated like any resource (`NAME_RE`, no `draft_`/`config`/`stubbase`/`env`/`auth`) before a path is built, non-scalar fields are dropped, and results are staged as `draft_*` only — a prompt injection must never overwrite tenant settings or go live unreviewed. `GOOGLE_AI_API_KEY` stays server-side, like `ADMIN_SECRET`.
- **Google wire-format facts** worth not rediscovering: there is no `role: "function"` (tool results ride a `user` turn carrying a `functionResponse`); model parts must be echoed back **verbatim**, since Gemini 3 signs reasoning with `thoughtSignature` and 400s without it; `responseMimeType` is mutually exclusive with function calling; and a function declaration may use an open `{type: "OBJECT"}` for dynamic record shapes. `AI_MODEL_NAME` must name a model that supports function calling — the Gemma family does not.
- `sites/landing/`: Astro 7 + Tailwind v4 + `@astrojs/sitemap`, client JS limited to six blocks — the theme-and-session pre-paint/toggle script in `BaseLayout.astro`, the Home "Try it live" runner, the Home Google One Tap prompt, the guides' two (the index's search + load-more filter, and the guide rail's scroll-spy), and the pricing page's donation amount control. No libraries; every one degrades to a working page with JS off (FAQ accordion and the header's nav dropdowns are native `<details>`; `ThemeToggle.astro` carries no script, its click is delegated from that one listener). Shared SEO head + JSON-LD lives in `src/layouts/BaseLayout.astro`; `src/layouts/Layout.astro` adds the Nav/Footer chrome around it.
  - **The one third-party script, and it is loaded conditionally.** Google's `gsi/client` is fetched by Home's One Tap module, not by a tag in the markup, so the decision not to prompt is also a decision not to call Google: a visitor carrying the `stubbase_session` hint, or a build with no `PUBLIC_GOOGLE_CLIENT_ID`, makes no request to Google at all. Keep it that way — a tag in the markup would load it for signed-in visitors before any guard could run. Nothing else on this site may pull a third-party script.
  - **Theme**: dual light/dark. `BaseLayout`'s `is:inline` head script resolves `stubbase_theme` cookie → localStorage → OS preference and stamps `.light`/`.dark` on `<html>` before first paint (the cookie comes first because it is the copy the *dashboard* can also write; the resolved value is written back to both, so the two converge) — it must stay inline and in `<head>`, or the page flashes the wrong theme. Dark is the bare `:root` in `global.css` on purpose, so a JS-off visitor or a non-JS crawler gets the brand default; light is the opt-in layer. Shiki runs a `{ light, dark }` theme pair under `defaultColor: 'dark'` for the same reason — set in **both** `astro.config.mjs` (markdown fences) and `CodeBlock.astro` (hub pages); keep the two in sync.
  - **The nav renders both auth states, and CSS picks one.** The same pre-paint script stamps `.signed-in` on `<html>` when the `stubbase_session` hint is present, and `global.css` hides the other `[data-auth]` wrapper (`display: contents`, so each variant's own responsive classes still apply). Nothing is fetched and nothing is swapped in after paint — the site is static and the session lives on another origin, so there is no request to make. With JS off nothing is stamped and the logged-out nav shows, which is also what a crawler should index. A stale hint costs one redirect to the dashboard's login page; the SPA clears the cookie when it sees the 401.
  - **Hub-and-spoke content**: hub pages (`/`, `/pricing`) are hardcoded `.astro`; the Solutions / Features / Compare spokes are Markdown in `src/content/<collection>/`, typed by the strict `seoSchema` in `src/content.config.ts` (Astro 7 loader API — config filename is `content.config.ts`, *not* the legacy `content/config.ts`) and rendered through `src/layouts/MarkdownLayout.astro`, which emits TechArticle + BreadcrumbList JSON-LD. Add a spoke by dropping in a `.md` file and one entry in `src/lib/nav.ts` (the single nav source of truth, read by both Nav and Footer).
  - **Guides** (`/guides`, `/guides/<slug>`): its own collection under `src/content/guides/`, rendered by `GuideLayout.astro` (**TechArticle** + BreadcrumbList JSON-LD, `og:type=article`, `dateModified` always emitted; the index is a CollectionPage wrapping an ItemList). The route is `/guides` and not `/blog` deliberately — these are evergreen procedures, and a `blog` URL tells a reader and a crawler that the page is chronological and ages. `/blog` stays unclaimed for genuinely dated posts. Three conventions are load-bearing. Screenshots ship **after** the prose: a figure is written as `<figure class="shot shot--pending">` with a drawn frame naming the file it waits for, and the build warns while any frame is still empty — swapping in `<img>` is the only edit. Card artwork is **drawn, not photographed**: `.post-tile` sets the post's own title and tag on a tinted ground, so a post needs no illustration and `thumbnail` overrides it when one exists. And the byline is the organisation, never a person — the JSON-LD author is an Organization, so changing the label changes the schema.
  - **Shipping something user-visible has a ritual, and it is not a blog post.** Three shelves, by how long the content stays true:
    - **`/changelog`** — every release, one entry, newest first. Add an object to the top of `src/lib/changelog.ts`; there is no per-release route, because a release note has no life of its own at its own URL. Dated, never versioned: this is a hosted service and there is no build number for a user to pin.
    - **`/features/<slug>`** — anything that changes what the product *is*. This is the durable artifact: the announcement decays, the feature page ranks and gets stronger each time it is revised. Add or update the spoke, then link it from the changelog entry's `href`. **A feature spoke is not shipped until it is in `src/lib/nav.ts`** — the nav is the tracking list, and a page missing from it is a page nobody finds.
    - **`/guides/<slug>`** — the recurring how-to a release creates ("how do I get those keys?"). Evergreen, so it never carries release framing.
    `/blog` is deliberately unclaimed. Release announcements do not go there; they go in the changelog and the feature page. It exists for the two things that genuinely have a date in their meaning — engineering write-ups and positioning arguments, the posts written to be *posted* somewhere — and it should stay unbuilt until the first of those is written, because an empty blog is invisible while a stale one is a signal.
  - **The "AI Summary" panel is generated out of band and committed.** `bun run scripts/ai-summary.ts` calls the provider once per guide and writes `aiSummary`/`aiSummaryModel`/`aiSummaryHash` into that post's frontmatter; the site build never calls an AI provider, so it stays reproducible and needs no key. `aiSummaryHash` fingerprints the body the summary was written from — `--check` fails when a guide has drifted from its summary, which is the only thing keeping the panel's claim honest. Regenerate after editing a guide's body, and read the diff before committing: it is published prose that no human wrote.
  - **`/pricing` is in a launch state, and it is temporary.** There is no payment gateway yet, so the two paid tiers carry `comingSoon: true`: priced and spec'd in full but struck through, badged "Not active yet", and with the CTA replaced by an inert element rather than a dead `<a>` (a link that goes nowhere still looks clickable and still gets crawled). "Most Popular" is suppressed on a tier nobody can buy, and the Offer JSON-LD says `PreOrder` rather than `InStock` — the prices are real and worth publishing, but claiming they are purchasable is not. Free is genuinely live and keeps a working CTA. Flip `comingSoon` per tier when billing is wired; nothing else on the page needs to change.
  - **`/pricing` is one argument, not two pitches.** Free to try → donate to keep trying → here is what billing will look like. The donation block sits *above* the tiers and every band shares the page ground: a tinted `bg-section` under one of them drew a line that made the donation read as an unrelated ask. Space separates them, per the rule above.
  - **The donation control is UI only, and must stay honest about that.** `#support` on `/pricing` takes an amount ($5–$1000) through a slider *and* a number box over one value — the slider for a figure you do not have in mind, the box for one you do. The track is **exponential**, not linear: on a straight 5→1000 scale every amount anyone actually picks would share its first 4.5%. Clamping happens on `change`, never on `input`, or typing "1" on the way to "10" rewrites it to "5" mid-keystroke. The button is disabled and says so, and **no card or credential field goes on this page** — checkout belongs to whichever provider is chosen, and this hands off to it.
  - **Never put a breadcrumb trail on a landing page.** Not on hubs, spokes, guides, the changelog — nowhere. The nav already says where you are, and a "Home / Guides" line above the H1 spends the most valuable row on the page repeating it. The `BreadcrumbList` JSON-LD stays (it is invisible and describes real hierarchy); only the visible trail is banned.
  - **Separate bands with space, not rules.** A hairline directly under a title or around a byline is the reflex to reach for and it makes a hero look like a form. Padding already does the work; keep rules for genuine table-like structure (the changelog's release rows, a list's dividers).
  - **The closing CTA is a card, and the footer owns it.** Pass `cta` to `Layout` and the footer renders it: a bordered panel holding the heading and body on the left and the button on the right. The footer drops its own top border when a CTA is present, since the card's edge already draws that line. Never hand-roll a second one in a page, and never pass `cta` *and* build your own: two closing calls to action read as two footers.
  - Copy on these pages is SEO/RAG-tuned: H2 wording, code blocks, and vocabulary are exact-match targets — don't reword them casually. Code fences are highlighted at build time by Shiki (`CodeBlock.astro` for hardcoded pages), never a client-side highlighter.
- `sites/dashboard/`: Vite + React + TS SPA — shadcn/ui (add components with `npx shadcn@latest add …`; `bunx shadcn` hangs), Zustand for UI/auth state, TanStack Query for all server data (`src/lib/api.ts` is the only fetch layer). On logout: reset workspace store *and* `queryClient.clear()` so no cross-user cache leaks.
  - **Which project is open lives in the URL, and only there.** The route is `/p/<tenantId>`; `hooks/projects.ts` reads it with `useParams` and the workspace store holds no project id at all. It used to, which meant a reload had nothing to restore from and the Editor silently adopted the first project — every refresh threw you back to the top of the list. `/` is the same screen with no project named and redirects to the first one, which is where login, signup and the OAuth callback all land; an account with **no** projects stays on `/` and gets `NoProjects`, and a project id on such an account is redirected away so a stranger's id cannot sit in the address bar being re-served on every refresh. **An id that is not in your list must never fall back to the first project**: `useCurrentProject` returns undefined and Editor renders `UnknownProject`, because quietly showing a different project misrepresents whose data is on screen. Putting the tenant id in the address bar makes a project link copyable, so the boundary is the Dashboard API's ownership check, never the SPA — `tests/dashboard-api.test.ts` covers every per-project route from one shared matrix (anonymous → 401, another account → 404), and a new `/projects/<id>/…` route means a new row in it.
  - **The APIs rail lists routes, and a route is not always a file.** `lib/endpoints.ts` derives the list from the project's resources *and* its live config: CRUD verbs per resource, plus the `auth` group (`POST /auth/signup|login|change-password|forgot-password|reset-password`) when the deployed config has `AUTH_ENABLED=true` — `auth` is a reserved name on the core, never a resource, so nothing in `resources` would ever have produced it. `hooks/endpoints.ts` reads that config with `?source=live` (see the Dashboard API invariants) and both the rail and the editor pane resolve a selection from the one list, so they can never disagree about whether a conditional route is there. An endpoint is identified by **path**, not resource + method: the auth group holds two POSTs. Anything with no file behind it carries its own request sample, and must not fetch a resource — reading `auth` on the public plane is a 403.
  - **`rbac.json` appears in the Files rail's `system` folder only while `RBAC_ENABLED` and `AUTH_ENABLED` are on** in the `.env` being edited (`rbacEnabled`, `lib/rbac.ts`, read as the core reads it), and is edited like the `.env`: JSON, Save stages a draft, Deploy puts it live, and a refused save shows the core's reasons. With no rules, Create starts from `RBAC_EXAMPLE` (`lib/rbac.ts`). The role picker in `system/users.json` offers the *deployed* rules' roles (`useLiveRbac`, minus `guest`) — or `user`/`admin` without rules — since those are what the API accepts.
  - **The Files rail has a read-only `system` folder.** It lists what `GET /projects/<id>/system` returns and opens a file with Refresh and nothing else — no Edit, no New, no Delete, matching the API. Everything it reads sits under the `['system', tenantId]` query key, and a playground Send to an auth route invalidates that key, since those routes are what write the files. `config.json` lives in `system/` on disk but is still edited through the `.env` item, not shown twice.
  - **The Live tab is an API playground, and three rules shape it.** *It is real traffic*: `runRequest` calls the public plane like any client, so a playground request is metered, logged and answered as theirs would be — never route it through the Dashboard API or `_admin`. *It calls only the route the rail shows*: method and path come from the selected endpoint, and the user edits only the record id, query params, the headers and the body. `lib/playground.ts` holds that, React-free so `tests/playground.test.ts` can import it: the id is percent-encoded into one segment and `.`/`..` are refused (the URL parser collapses those before a request leaves, encoded or not), query params go through `URLSearchParams` and only on reads. Headers are a **fixed set** because they must be — the core's public preflight allows `content-type`, `authorization` and the four `x-stubbase-*` headers, and a browser will not send a cross-origin request with anything else; add a header on either side and the suite checks it against a real core's preflight. *It tests the deployed API*: a resource the rail lists but the API does not route yet (saved, never deployed — `putFile` adds it to `resources` immediately) keeps its Send disabled, decided by the `?source=live` read (`useLiveResource`, which a deploy invalidates). The tenant token a successful `/auth/signup|login` returns is adopted for the protected routes and lives in the workspace store only, cleared by `reset()` on logout — it is a real credential for the project's API. There is no confirmation before a DELETE, matching every other client. A Send is added to the Usage panel the moment it returns rather than two once-a-minute hops later (the core's flush, then the panel's poll): it raises a *floor* (`lib/usage-floor.ts`) that every fetch is shown at or above until the server's figures reach it or it lapses after three minutes — adding the Send once would let a poll landing before the flush take it back off. Only what the core meters raises one: `countsAsUsage` mirrors the core, excluding no response and the platform's own refusals (recognised by their JSON, since a QA project's requested 503/429 is counted), and the suite holds it against a real core's responses.
  - **The Logs pane keeps a per-tab copy of the request log in sessionStorage, and it must never hold a credential.** `lib/log-storage.ts` is the only writer, and it writes only while the Logs pane is open — `useLiveLogs` is mounted by that pane alone — so what was on screen survives a reload, a trip to the Editor, and the save or deploy whose eviction drops the core's ring. sessionStorage, not localStorage, deliberately: per tab and gone with the tab, so two tabs on one project each keep their own copy and never overwrite each other. Three rules, each in `tests/log-storage.test.ts`. `/auth/*` entries are stored **without bodies**, because a signup or login response carries the project token that the workspace store otherwise keeps in memory only. **Clear sticks**: it records the newest *server* timestamp it cut — never the browser clock, which may run ahead — so the core's replay on the next connect cannot bring older entries back. **Logout forgets every copy and disarms every open store**, because the pane unmounts a render after logout and its final flush would otherwise write the logs straight back. None of it touches the core's ring.
  - **Starter examples are two lists, and the split is load-bearing.** `STARTERS` in `src/lib/starters.ts` means *seedable* — real records, and `tests/starters.test.ts` seeds each into a live core and runs its advertised query. `PLANNED_STARTERS` is the six placeholders that fill the empty state out to nine cards; they hold resource **names** only and render disabled and dashed. Writing one for real means moving it across, which is also what puts it under the suite. Never give a placeholder an empty `resources` map to smuggle it into `STARTERS`.
  - **The SPA never keeps its own copy of the plan table.** `/auth/me` returns the entitlements already resolved (`features`, `monthlyRequests`, `planName`); `hooks/plan.ts` only reads them. Everything the UI does with them is presentation — the server refuses an off-plan call regardless — so a stale value costs a worse error message, never access. Off-plan controls are **disabled, not hidden** (the Co-Pilot composer, the only one left), each with a `PlanNotice` saying why: a control that vanishes teaches nobody it exists, and a disabled one with no explanation reads as a bug.
  - **Theme**: dual light/dark, resolved by the inline script in `index.html` *before* the bundle loads, which stamps `.light`/`.dark` on `<html>`; `src/stores/theme.ts` adopts that and owns it from there, writing every change to **both** localStorage and the cross-origin cookie. The auth pages carry their own toggle (`AuthLayout`), since the shell's `TopBar` is not on screen before there is a session. The class must always be stamped explicitly — the shadcn `ui/` primitives key off `dark:`, which needs `.dark` genuinely present. Two places sit outside the token cascade and need the theme handed to them: `ui/sonner.tsx` (renders in its own portal) and `JsonEditor.tsx`'s CodeMirror `dark` flag, swapped via a `Compartment` so reconfiguring never discards the document's undo history. Every colour *inside* the CodeMirror theme is a `var(--token)` and re-resolves on its own.
- Design system (both frontends): zinc/emerald — `zinc-950` page, `zinc-900` surfaces, 1px `zinc-800` border on every surface, no shadows, emerald buttons always with **black** text, Inter (`font-sans`) + JetBrains Mono (`font-mono`) self-hosted via Fontsource, Lucide icons. Theme tokens are mapped in `sites/dashboard/src/index.css` and `sites/landing/src/styles/global.css` — restyle there, not per-component. Both frontends ship **light and dark**, and share a token vocabulary (`--subtle`, `--faint`, `--primary-ink`, `--syntax-*`) so the two read as one system.
  - **The palette is three layers, and only the first inverts.** Surfaces are mechanical — but do not flip the elevation: dark cards are *lighter* than the page (`zinc-900` on `zinc-950`), so light keeps that direction with white cards on a `zinc-50` page, never a grey card on white. Brand emerald does not invert: `emerald-500` is 8.3:1 as a fill under black text in either theme (so that rule survives) but only 2.5:1 as *text* on white, which is why `--primary-ink`/`--primary-accent` resolve to `emerald-700` in light. Status and syntax colors must be re-picked per theme and not by a uniform step — `amber-400` is 1.7:1 on white, so amber and rose go to 700 where sky can sit at 700 for a different reason. Tinted callouts (`--primary-soft`) are their own tokens rather than `/10` opacity modifiers, because a fixed alpha does not read the same over `zinc-950` as over white.
  - Where the two differ: landing puts dark on the bare `:root` (it has a JS-off path to protect); the dashboard keeps shadcn's `:root`-is-light convention, because nothing renders there before the pre-paint script has run anyway. The dashboard also carries a longer neutral ramp — eight text steps (`--heading` → `--ghost`) and three status families (`--danger-*`/`--warning-*`/`--info-*`) that landing has no use for. Its two dimmest text steps deliberately *compress* in light: a straight inversion would leave ~51 uses at 2.9:1 on white.
  - When touching colors in either frontend, the correctness check is that **dark renders unchanged** — every token's dark value equals the literal it replaced. If dark shifts, the swap was wrong.
- `sites/*/dist/` is gitignored; Ansible copies it from the local checkout, so **build both sites before deploying**.
- `caddy/Caddyfile` (production, structure is spec-frozen) and `caddy/Caddyfile.dev` (local, mirrors it on `*.localhost`). Keep the two in sync when routes change.
- `deploy/files/*.service`: sandboxed units — `ProtectSystem=strict` with exactly one `ReadWritePaths` each (core → tenants dir, app → SQLite dir). If a service needs a new writable path, add it there deliberately.
- Secrets never go in unit files or git — only `/etc/stubbase/stubbase.env`, templated by Ansible from `STUBBASE_ADMIN_SECRET`.

## Writing FEATURES.md

`FEATURES.md` is the user-facing feature list, and it is the one document here
that does **not** use the brand voice in PRODUCT.md. Write it in plain second
person — what *you* do, what *you* get ("add a JSON file to your project and the
CRUD endpoints are created for you"). Say "project", never "tenant". Leave the
internals out: RAM caching, write-through, eviction, pipeline stage names and
draft file naming are `README.md` / `ENVIRONMENT.md` material. The technical
voice stays correct everywhere else.

Three top-level groups, and a feature belongs to exactly one of the first two:

1. **User-level** — what a *project's* API does, i.e. what the person calling
   the endpoints experiences.
2. **App-level** — what Stubbase itself does: dashboard, accounts, Co-Pilot,
   metering, keys.
3. **Env settings** — the central reference, one table per feature.

**A feature entry is written in three parts, in this order:**

1. **What it is and how you use it.** Prose plus the endpoints or requests a
   user actually writes. Lead with the outcome, not the mechanism.
2. **Its env keys, one heading per thing you might want to do** —
   "To enable this feature, add to your `.env`:", "To control how long a login
   lasts:". Under each: a fenced env block, then what it does, then the other
   possibilities (a small table of values earns its place when the choice is a
   trade-off, as with `AUTH_JWT_TTL_SECONDS`). The enable switch always comes
   first, and keys that are useless apart — an OAuth client id and its secret —
   share one block, because they are one decision.
3. **A table in section 3**, listing every key of that feature with an example
   value and what it does. The feature's enable flag is always the first row.

**Sub-levels: what to group, what to split.** A feature gets sub-sections only
when it has genuinely separable parts. Decide with these, in order:

- **Split when the parts switch on independently.** Google login and GitHub
  login each have their own key pair and either can run without the other, so
  they are `1.3.1` and `1.3.2`. Email and SMS notifications will split the same
  way — different credentials, either one alone is a working setup.
- **Group when one switch turns all of it on.** The four chaos headers
  (`delay`, `status`, `error-rate`, `empty`) are one feature behind `QA_MODE`,
  not four; the list query params (filter, `_sort`, `_page`, `_expand`) are one
  feature behind nothing at all. Parts that cannot be enabled separately are
  paragraphs or table rows, never sub-sections.
- **Keep what is common to every part in the parent.** Auth is `1.3` and that
  is where email-and-password lives, because the switch, the token, the public
  routes and the TTL are the base every login shares. A part that everything
  else depends on is not a sibling of the things depending on it.
- **Never split below one decision.** An OAuth client id and its secret are
  useless apart, so they share one block. If a sub-section's env example is a
  single key that nobody sets on its own, it should have been a row in the
  parent's table.
- **Stop at two levels.** `1.3.1` is as deep as this document goes. Needing
  `1.3.1.1` means the parent was really two features — split it at the top
  instead.

Section 3's tables are numbered independently of section 1, because a feature
with no env keys gets no table at all — relations (`1.2`) configure nothing, so
auth stays `3.1`. Within a table, the sub-numbers do track the feature's:
`3.1.1` is the table for auth's first sub-feature, and the parent's own keys sit
in a table directly under `3.1`. Every table names and links its feature in a
`Feature:` line, which is what actually ties the two sections together — so
renumbering section 1 means fixing those links, not renumbering section 3.
Sub-features take `####`; the "To …" env headings are `#####` everywhere,
including in the parent, so a heading's level always says which of the two it is.

When a key serves several sub-features but not all of them, **repeat it under
each one** and say it is shared — clarity for the person reading a single
sub-feature beats not repeating yourself. `AUTH_OAUTH_REDIRECT` appears under
both Google and GitHub, and does not appear in the parent, because password
login never redirects. Only lift a key into the parent when it genuinely applies
to every path below it, and check the code before deciding which it is: the
answer is where the key is *read*, not where it looks like it belongs.

**Say what a sub-feature depends on, every time.** Google login needs
`AUTH_ENABLED=true` as well as its own pair — `handleAuth` 404s before it ever
reaches the OAuth branch — so each block repeats the switch in its env example
instead of trusting the reader to have read the parent section.

**The duplication between parts 2 and 3 is deliberate — do not collapse it.**
They serve different readers: someone setting the feature up for the first time
reads the walkthrough, someone who already runs it and wants to check a key name
reads the table. Cross-link the two section headings, but do not add prose
telling the reader the same keys appear elsewhere.

Two standing rules for the content itself: state a feature's *intended*
behaviour and add a dated `> **Known issue:**` blockquote when the shipped
behaviour differs (never quietly document the bug as the design), and never
describe a plan-gated feature as freely available — check `PLANS` in
`apps/dashboard-api/server-app.ts`.
